creaite Notes: a light wiki

Research, feedback and three ways to place it. Sample projects and people from the development vault. Mockup only, 13-10-2026.

Worth doing, if notes stay small, passive and linked to the record.Build it as Notes (not "Wiki") inside each project, with a capture drawer that works from any page. Replace the hand-built Current state editor with Tiptap at the same time, so the wiki and Current state share one editor and one Markdown format.

What it solves

Today Alan's ad hoc thinking has nowhere good to go. Project memory (CLAUDE.md) is meant to stay at about one page and changes only by proposal. Quick capture (FR-71) is a different job: it sends a note into cx-minutes for extraction. Stakeholder observations, negotiation positions, "how this client works" and lessons learned end up in OneDrive or nowhere, so search and ask creaite can't find them.

Where it could go wrong

  • A second record. The biggest risk. If someone writes "Omar owes the SOW by Friday" in a note, it's an action that the tracker doesn't know about. Rule: notes never hold actions, risks or decisions. They point at them with live item chips (FAL-R-004), and a Make this an action option on a selected line turns it into a proposal.
  • Overlap with project memory. Keep the split clear. Memory is the short brief that Claude reads every run. Notes are Alan's longer working material, which Claude reads when a question needs them. Later, an "Add to memory" button could propose a trimmed line.
  • Another place to file things. A new rail item and a folder tree add filing decisions. Placing notes inside the project, with one Unfiled list, keeps the choice to "which project?", which creaite can usually guess.
  • Notes left behind. Personal wikis rot when nobody reads them. Surface notes where work happens: Prep pages, the item peek ("2 notes mention this"), search and ask creaite's answers.
  • Confidential material. Notes are internal by default and never go in a client report, like documents (BL-93).

Wiki practice that fits creaite

  • Capture first, organise later. Practitioners agree on a single inbox, sorted later. Here that means the drawer saves to the project it guesses, or to Unfiled, in one keystroke.
  • One topic per note, linked. Short notes about one subject, joined by [[links]], search better than long logs.
  • Backlinks matter more than folders. "Mentioned in" on every note, person and work item does more than a deep tree. Allow at most one level of grouping.
  • Templates only where structure has proved itself. Start with four: Blank, Stakeholder, Lessons learned, Working session. Add more later.
  • Add an index once there are many notes. Show pinned notes at the top of the list rather than build a contents page.
  • Plain files. Markdown with a small front-matter header, so notes are readable in Finder, OneDrive and git, and still work if creaite is gone.

Rich text editor: the options

Constraints: Chrome only, Markdown stored, bundled locally in system/templates/vendor/ (no CDN, nothing built at run time), MIT-style licence, and it must handle [[link]], @person and item-ID pickers.

Current state (BL-47, FR-63), the minutes review text sections (BL-56), Prep focus notes (BL-286), the Draft email preview (BL-224), item descriptions in the peek, and the new Notes. Why this is the recommendation

  • Collapsible list: « hides it to a slim strip and » brings it back (⌘\ too). The choice is remembered per browser, and the note widens to fill the space.

AI rules

  • One route on the live server, /api/edit/ai, with the existing "Make it executive" as one of its options. Claude runs headless with no tools: it sees only the selected text, the option and the project's name, people and open item IDs (to make chips). It can't read files or mail, and can't write anything.
  • Same plain-code fact check as BL-106's rewrite: any date, number, name or item ID that was lost or added is flagged under the suggestion.
  • Available in every editor. Each place picks its options: Current state keeps the executive voice first; Draft email adds "More formal" and "Warmer".
  • A note marked Confidential asks once before it sends text to Claude.
  • Counts only (offered, accepted, discarded) go to draft-stats.json, never the text.

Editor rules, shared everywhere

  • The same toolbar and keys as today's Current state editor, so nothing has to be relearnt. The pickers ([[, @, #, /) are the new parts.
  • Each place turns on only the features it needs. Current state: no tables or checklists, because Word reports can't take them yet. Draft email: no wiki links.
  • Item chips always show live state from the tracker. The Markdown holds only the ID, so a note never goes out of date.
  • Paste is cleaned to the Markdown subset. A pasted link to a Teams message or mail becomes a source link.
  • Round-trip tests: every existing CLAUDE.md Current state must load and save back byte for byte before the switch.

A note from a conversation becomes changes to the tracker: new items, updates to existing ones, milestone moves and project information. The panel is the review. You tick, edit and apply in one place, and Undo is there afterwards. Save for later sends them to Review instead.

Three ways in

  • ✦ Find updates on any note: reads the whole note and fills the panel above. Lines already sent are skipped, so you can run it again after adding to the note.
  • One line: select it, then AI ▾ › Make this an action (or a risk, decision or update). The same panel opens with just that line.
  • While typing: a checklist line with an @person and a date gets a faint dotted underline, meaning "this looks like an action". Clicking it proposes the action. It never stages anything on its own.
  • From the capture drawer: Done keeps the note; Done and find updates also opens the panel. This replaces the Note / Quick capture switch.

How it works underneath

  • The same engine as quick capture (FR-71, cx-minutes) and cx-edit, given a note as the source. The existing checks run at staging: repeats of existing items (BL-221), probably-done evidence (BL-218) and vague actions (BL-221).
  • Hedged words ("probably", "might", "to confirm") never move a milestone or change health. They become a confirm action and an early warning instead.
  • Each proposal's source is the note and the paragraph, e.g. projects/…/08 Notes/Catch-up with Omar.md#p4. In Review, the source link opens the note at that line, highlighted.
  • What was sent is recorded beside the note, not in it: system/staging/notes-sent.json (path, paragraph fingerprint, item IDs). The note text stays as you wrote it, and a margin tick (✓ FAL-A-024) shows lines that became items.
  • Apply, not Send to Review. Ticking a row is your approval. Apply writes the ticked rows as already-approved proposals (source_run: "note", as dashboard edits are today) and runs tracker.py apply through the live server. It's one apply, so Undo reverses all of it. Unticked rows are dropped and never staged.
  • The bulk rule still holds. New risks, new decisions, milestone moves and health changes always start unticked and must be ticked one at a time. Routine updates (due dates, done, owner, a new action) start ticked.
  • Click a row to edit it in the same peek layout as Review (BL-177): owner, date, wording, workstream. Every row passes the same schema validation; a row that fails shows why and stays unticked.
  • Save for later puts the ticked rows in Review instead, for when you want to think it over. If the live server isn't running, Apply does the same and says so.
  • A note marked Confidential marks its items Sensitive.
  • It runs only when you press it. It never runs unattended or from the sweep.
