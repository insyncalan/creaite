# cx-sweep

Tunable values (due time, first-run look-back, sources, Possible matches) come from `system/config/settings.json` (`sweep`). The defaults below apply if the file is missing.

**Projects by name (BL-101):** refer to a project by its full name in everything Alan reads (summaries, tables, messages, file names, drafts). The short code appears only inside a work item's ID (`ABC-A-003`) and in a command he can type; `tracker.project_label(code)` gives the name.

Find project items in mail and Teams, and propose them for review. Proposals only; this skill never writes to the database.

Scripts (run from the vault root) handle the exact parts: `system/scripts/run sweep.py due | window [--days N] | lock | unlock | ignore <messages.json> | vip addresses|record|seen|list | expected <CODE> [--date …] [--subject "…"] [--text "…"] | stage <sweep.json> | done --started "…" [--normal] [--summary "…"] | fail --message "…" | transcripts todo|record <facts.json>|show | calendar <calendar.json> | calendar-window` (see its help for `sweep.json`).

Read these first:
- `projects/_portfolio/project-register.md`
- `projects/_portfolio/people-register.md` (BL-55; every run: sender and attendee addresses and names map to a full name)
- `.claude/skills/cx-minutes/references/project-matching.md`
- `.claude/skills/cx-minutes/references/tracker-conventions.md`
- `dev/staging-format.md`

## Triggers and window

| Trigger | Window |
|---------|--------|
| "sweep" or "sweep mail" | Since the last successful sweep (`system/staging/last-sweep.txt`) |
| "sweep mail for ABC" | Since the last sweep (never further back than `sweep.max_lookback_days`, 3), project ABC only. Does not advance the timestamp |
| "sweep mail for the last 7 days" | The stated window. Does not advance the timestamp |
| "sweep the <subject> thread" | That thread. Does not advance the timestamp |
| **Session-start catch-up** | If the last successful sweep is before today's 07:00 and it is now after 07:00, run a normal sweep first and say "Sweep due since 07:00, running now…" |

- **Window:** `sweep.py window` (or `window --days 7`) gives the start and end; the first ever run looks back 14 days. **Lookback cap (#146):** a since-the-last-sweep window (the daily sweep and the catch-up included) never reaches back further than `sweep.max_lookback_days` (default 3; Settings › Advanced), so after a long gap mail and Teams are read for the last 3 days only. `window` then prints a `capped` object; **say its `note` in the summary** ("Read the last 3 days; 2 older days not read. Say 'sweep the last 7 days' to include them."). "Sweep the last n days" (`--days n`) overrides the cap for that run. The cap does not touch the calendar.
- **Catch-up from Close the day (BL-295):** the live server may start this skill headless as Close the day's catch-up sweep (`day.catchup_sweep`, when the last sweep is older than `day.catchup_after_minutes`). It is a normal sweep with no CONFIRM step: it only stages proposals for Review, its guard refuses every record command (apply, approve, reject, undo) and any write outside `system/staging/drafts/`, and it may run `propose.py people map` only on its own draft there. It never runs in the development repository.
- **Typed in ask creaite (BL-309):** when Alan's whole message is a sweep request (one of the triggers above, or "refresh calendar"), the live server runs it under the same guarded `sweep` mode as Close the day's catch-up: typing it is the confirmation, so stage directly with no CONFIRM line; apply, approve, reject, undo and `propose.py stage` stay refused, and Alan approves the proposals in Review. A message that asks for more is a plain chat under the usual rules.
- **One sweep at a time:** `sweep.py lock` at the start and `sweep.py unlock` at the end (also after a failure). A lock under 30 minutes old means another sweep is running: wait.
- Note the run's start time; it becomes the new timestamp on success.

## Sources

Outlook **Inbox** and **Sent Items**, and Teams **chats** and **channels**, through the Microsoft 365 connector. Plus Alan's Outlook **calendar** (`sweep.sources.calendar`), read only for the dashboard's Today day view: it never produces proposals.

## Flow

0. **VIPs first** (see "VIPs" below): record anything the VIPs sent since the last check.
1. **Search by project signals** from the register: `[CODE]` in subjects, project names and aliases, client email domains, key stakeholders, registered Teams channels, keywords, and Outlook categories named after a project code (set by Alan's server-side rules; a **strong** signal). Ignore anything that matches no project.
2. **Apply the ignore rules** (`sweep.ignore` in settings, BL-97; `sweep.py window` lists the ones in force). Before reading any thread, write the messages found to `system/staging/drafts/messages.json` as `{"named": false, "messages": [{"kind": "mail|teams|calendar", "subject", "from": "<name> <address>", "channel", "sensitivity"}]}` and run `sweep.py ignore` on it: drop every message not in `keep` (the command deletes the file itself). Ignore wins over project matching, so an ignored message is dropped even if it names a project. The built-in rule drops anything marked **private** or personal; also **skip confidential messages** (sensitivity labels). Set `"named": true` (and `"named": true` in `sweep.json`) when Alan named the thread ("sweep the <subject> thread"): then nothing is ignored. The script counts what it drops, and `sweep.py stage` checks each item's From and Subject again as a backstop. Never decide an ignore yourself, and never drop a message silently.
3. **Read each thread as a unit,** but extract only from messages newer than the window start. Never re-propose items already proposed from the same thread: check open items, the `rejected` table and previous proposals. Read each matched project's reject reasons as guidance (BL-133: `system/scripts/run tracker.py read rejected --project <CODE> --days 90`, the reason and the item's text): avoid the same kind of item again; nothing is blocked by them beyond the exact fingerprint.
4. **Extract** (workstreams from the matched project's own list only, by name, keyword, alias, lead or channel: see the workstream rule in the conventions, BL-58):
   - **Actions,** including requests made to Alan and commitments Alan made in Sent Items or chats. Set `owner` to Alan's full name (settings `identity.name`) for both. Only when promises are on (settings `promises.from_sweep`, see "Promises" below), a commitment made in passing ("I'll send it over by Friday") is a **promise** instead; never both. While they are off (the default), treat it as an action, as before.
   - **Decisions** confirmed in writing.
   - **Risks, issues, assumptions and dependencies** (RAID `type`).
   - **Status signals,** added to `status_signals`.
4a. **Expected items: propose updates, not repeats (BL-297, as cx-minutes 4a).** For each project a message matches, read its open items once per sweep with `system/scripts/run sweep.py expected <CODE> --date <the message's Sent day> --subject "<its subject>" --text "<what it asks, in your words>"` (read only; never query the database yourself). It lists the project's open actions, RAID items and decisions needed (the same JSON as `minutes.py expected`), best matches first, each with a `match` (Very likely or Possible and why: the item's ID, the same thread, a person, a less common word, its timeframe), and leaves out items raised after the message. A message that **moves one of them forward** (rebooked, re-dated, progressed, blocked, waiting on someone) becomes an **update** to it in `sweep.json`, never a new item: `{"op": "update", "table": "actions" | "raid", "id": "ABC-A-007", "set": {"latest_update": "DD-MM-YYYY: <what happened, in a few words>", "due_date": "YYYY-MM-DD"}, "why": "<the few words it rests on>", "source": "<the message's structured source>"}`. The latest update is dated the message's Sent day; give `due_date` only when the message gives one ("next week" is the Friday of next week). An action may change `latest_update` and `due_date`, a RAID item `due_date` and `response_action` (only what the message says is being done); never the status (finished items are Probably done, below), owner, title or project. A message that merely mentions an item is left alone. An update of the date and latest update only is routine in Review; anything else is approved on its own.
5. **Match each item's project:**
   - strong and medium matches go into the normal batch;
   - weak matches go into a separate **Possible** section (`match: "possible"`), and Alan must choose a project before approving one;
   - on every medium, possible or two-project item, record `signals`: the sender address, the email domain, the Teams channel and any alias or stakeholder that pointed to a project (BL-28; see `project-matching.md`).
6. **Attachments:**
   - minutes or transcripts: copy them to `inbox/` for cx-minutes, which stays manual;
   - other documents: list them in the summary only (name, sender, date), so Alan can file them in `documents/` himself.
7. **Stage:** write the items to `system/staging/drafts/sweep.json`. Set `owner` (and a decision's `made_by`) to the person's **full name from the people register**: an email address (a sender, a recipient) or an alias maps only on an exact match. Run `system/scripts/run propose.py people map system/staging/drafts/sweep.json` (BL-55): it maps what matches exactly, and flags each name the register doesn't know with `unknown-owner` (never guessed). Then run `sweep.py stage` on it; it deletes the file itself once the proposal is written and checked (a failed stage keeps it). It skips items already open, rejected before or proposed before from the same message, adds `no-owner` and `no-due-date` flags, writes `proposed-YYYY-MM-DD-HHMM-sweep.json` (`source_run: "cx-sweep"`), validates it and prints the summary.
8. **Calendar** (normal sweeps, and "refresh calendar" on its own; skip if `sweep.sources.calendar` is off): search Alan's Outlook calendar over the window `sweep.py calendar-window` prints as `from` and `to`: **from today** to 7 days ahead (#146: a past meeting does not change, so a sweep never re-reads past days; `sweep.py calendar` keeps the past days already saved, which feed the Inbox's Meetings, BL-42; `from` is earlier only to fill a gap, when no calendar is saved yet or it was last fetched over a week ago). Say "calendar from today" in the summary. Mail and Teams keep their since-the-last-sweep window, capped as above. Leave out meetings Alan has declined and cancelled ones. Write `system/staging/drafts/calendar.json` as `{"days": {"YYYY-MM-DD": [{"id", "start": "HH:MM", "end": "HH:MM", "title", "where", "all_day", "private", "teams", "organiser", "organiser_email", "sensitivity", "recurrence", "body", "attendees", "attachments"}]}}`: `id` is the calendar event's ID; `start` and `end` **exactly as Microsoft 365 gives them** (an ISO date-time with its zone, or the `{"dateTime", "timeZone"}` pair), under the day they fall on in that zone: never convert times yourself, because `sweep.py calendar` converts them to the laptop's time zone and files each meeting under its local date (BL-107; "HH:MM" already in local time is accepted too); `where` is the room or "Teams"; `private` for meetings marked private; `teams` from the event's online-meeting flag (true for a Teams meeting), not from the "where" text; `organiser` is `true` when Alan organised it, else the organiser's display name; `organiser_email` its address; `sensitivity` normal, personal, private or confidential; `recurrence` in a word or two ("weekly"); **for meeting prep (BL-98)** `body` the invite's body as Outlook gives it (HTML is fine), `attendees` as `[{"name", "email", "type": "required|optional", "response": "accepted|tentative|declined|none"}]` and `attachments` the attachment **names** only (never open or save the files). Then, as the very next step, run `system/scripts/run sweep.py calendar system/staging/drafts/calendar.json`, exactly so: the relative path, nothing before or after it, never `cd`, `ls` or `cat` to check the file (use the Read tool if you must look); it deletes the file itself once the calendar is saved, and prints what it saved. If it is refused or fails, say plainly "The calendar was not saved" and why, and don't list the meetings in the chat as if it had worked (BL-268). The script does the rest: it drops events an ignore rule matches (private ones included, BL-97) and counts them, turns the body into plain text and **strips the join link, meeting ID, passcode and dial-in numbers** (never saved), keeps only the title and times of a **confidential** event (no body or attendees), maps attendees to the people register, and keeps the body to 20,000 characters. Everything stays in `system/staging/calendar.json` on the laptop; the dashboard embeds a body only in today's and tomorrow's Prep. A calendar failure doesn't fail the sweep; mention it in the summary.
8b. **Transcripts** (BL-42 phase 3; right after the calendar is saved, on normal sweeps and "refresh calendar"; skip if the calendar source is off): `system/scripts/run sweep.py transcripts todo` lists the meetings in the Calendar import window (recent past days included, #146: a transcript can arrive after the meeting, so this check still covers them) to look up: new ones, and any still *Not transcribed* (a transcript can appear hours later). It records in-person meetings as *No transcript* itself. For each meeting listed, retrying once if the connection drops:
   1. `outlook_calendar_search` for its title on its day, and take the event whose `id` is the one listed;
   2. `read_resource` on that event's `uri` (as returned): note `onlineMeeting.joinUrl` (online or not), `meetingTranscriptUrl` and `isOrganizer`. **Never keep the body, the passcode or the dial-in PIN**;
   3. if there is a `meetingTranscriptUrl`, `read_resource` on it **exactly as returned** (it carries this occurrence's start and end) and count `transcripts`. **Don't copy or keep the transcript text.**
   SharePoint and OneDrive search are not a fallback. Write the facts to `system/staging/drafts/transcripts.json` as `{"results": [{"id": "<the event ID>", "online": true, "uri": "<meetingTranscriptUrl exactly>", "count": 1, "error": null, "start": "…", "end": "…"}]}` (`online` false when there is no join URL; `count` the number of transcripts, or null if none was read; `error` "permission", "notfound" or "other" when the read failed). Then `system/scripts/run sweep.py transcripts record system/staging/drafts/transcripts.json`: it works out each status (*Transcript available*, *Not transcribed*, *No transcript*, *No access*) and keeps them in `system/staging/transcripts.json`, which the dashboard shows beside each meeting. Loading a transcript into `inbox/` is Alan's choice, from the dashboard, never the sweep's, **unless** `sweep.fetch_transcripts` is on (#250; off by default).
   **Fetch transcripts as they appear (#250; only when `todo` prints `"fetch_transcripts": true`).** A meeting listed with `"fetch": true` is one Alan could Process (ended, in the window, not confidential, not cleared, processed, in Review, loaded or fetched before); `todo` already leaves the rest out. Read it exactly as above, with **the same two Microsoft 365 reading tools Process uses** (`outlook_calendar_search`, `read_resource`) and nothing else: no SharePoint or OneDrive, and never a Microsoft 365 action. **Never copy, quote, summarise or re-type the transcript** (no AI works on it). When Claude Code saves the transcript read's result to a file ("Output too large… saved to: <path>"), add that path to the meeting's facts as `"result_file": "<path>"`; otherwise leave it out. `transcripts record` then writes each fetched transcript into `inbox/` itself, from that file, exactly as Load does (a meeting whose result came back inline stays *Transcript available* and is fetched on Process, as today), and prints `"fetch"`: each meeting's outcome (`fetched`, `failed`, `left`, or why it was left alone). When the sweep runs in the live server, the server keeps its own copy of each read and fetches from that, so nothing extra is needed. A confidential meeting is never fetched, whatever its listing says. Nothing reaches the tracker and no proposal is staged from a fetched transcript; cx-minutes stays manual. If Microsoft 365 can't be reached, carry on: `done` says so and the next sweep tries again.
9. **Finish:** `sweep.py done --started "<run start>" --normal --summary "<summary>"` for a normal sweep (`--normal` left out for a project, window or thread sweep, so the timestamp doesn't move). It adds "Fetched n transcripts" (#250, when the fetch is on and tried anything) and what the ignore rules skipped to the summary and the run log; show what it prints: "Sweep: 12 items (3 possible), 1 transcript to inbox, 2 documents to file — say review. Fetched 2 transcripts. Ignored 14: ToDo invites 9, humancapital 3, Anything marked private 2". **The dashboard is rebuilt by the script itself** (`stage`, `calendar`, `done` and `fail` each end with a rebuild, as an apply does), so the new items show on the page: don't run `build_dashboard.py` by hand. A dashboard that is already open notices the change by itself (within its health-check interval) and shows the new Review items, unless Alan is in the middle of an edit, so there is nothing to tell him to reload. If a rebuild fails it prints one note and the sweep's own result stands; say so if you see the note.

## VIPs (BL-99)

VIPs are the people the register marks in its **VIP** column (`sweep.py vip addresses` lists every address, a person's several addresses included). **Anything a VIP sends is never dropped:**
- **First, every sweep and every session start:** before the project search, search Inbox mail, Teams chats and channel messages, and calendar invites or updates **sent by** the VIP addresses since the `since` time `vip addresses` gives (the session-start check uses the same window). **The unit is the conversation, not the message (BL-334; mail threads too):** for each Teams chat or mail thread one of those messages belongs to, read the whole conversation since the `since` time (everyone's messages, not only theirs, plus a few earlier ones for context), its title, its participants and any attachment names. Write one object per conversation to `system/staging/drafts/vip-found.json`: `[{"kind": "teams|mail|calendar", "conversation": "<the Teams chat ID or mail conversation ID>", "title": "<the chat's or thread's own title, or null; never a generic 'Group chat'>", "from": "<name> <address> of the person who wrote", "people": ["<name> <address>", …], "last": "YYYY-MM-DD HH:MM of its last message", "link", "sensitivity", "attachments": ["<file names only>"], "summary": "<what it came to, one or two lines, at most 300 characters, your own words>", "items": [{"type": "action|decision|risk", "text": "<the item, verb-first for an action>", "owner": "<full name or null>", "due": "YYYY-MM-DD or null"}]}]` and run `sweep.py vip record system/staging/drafts/vip-found.json --found sweep` (`--found start-up` at a session start); it deletes the file itself. Report the outcome, not the to and fro: greetings, thanks and chatter are never an item, and a conversation with nothing actionable has `"items": []` (Today shows it as one quiet line). Never quote a message; for a private conversation give only `"summary": "private"` and no items. A **confidential** conversation is summarised like any other, in your own words, with `"sensitivity": "confidential"` (Alan, 15-10-2026): the card shows it marked Confidential, it stays internal, and anything made from it is never client-visible and carries the Sensitive label, so it never reaches a client report. The script keeps only conversations with a VIP in them, updates the same card when a conversation carries on, matches the project from the title first, then the people, the attachment names and the content (else "no project"), and stores no message text.
- **VIPs bypass project matching and every ignore rule**, including the private rule and the confidential skip in step 2: a private or confidential message from a VIP is alerted with its marker (its content is still not read into proposals; only the confidential one's alert carries your summary).
- **Items (BL-334 C):** a conversation summarised on Today is not proposed again: its candidate items wait on the card, where Alan makes one a work item (Create work item) or dismisses it. Give each item in `sweep.json` the `"conversation"` ID it came from; `sweep.py stage` skips an item from a conversation already summarised unless the item's message was sent after that summary. Anything else a VIP asks for is proposed as usual (step 4) when it matches a project; `sweep.py stage` flags it `vip`, so it sorts first in Review.
- **While the live server runs** it does the same check by itself every `vip.check_minutes` (read-only, Microsoft 365 search only), so this section's search is a catch-up, not the only look.
- Alan clears an alert with **Seen** on Today (or "mark the VIP alerts seen": `sweep.py vip seen --all`).
- **Private (BL-288):** who is a VIP is Alan's own judgement. Never write "VIP" or say who is one in a gist, a proposed item, its source, a status signal or the sweep summary; the alert and the `vip` flag are enough.

## Decisions needed (BL-53)

A separate step from the flow above; the flow's steps are unchanged. When a message or chat says a decision is needed ("we need a decision on…", "can you confirm the pilot extension by Friday?"), propose it as a **pending decision** in the same `sweep.json`:
- `{"table": "decisions", "values": {"project": "ABC", "decision": "<the decision to be made>", "status": "Pending", "date": "", "made_by": "<full name of who is asked>", "needed_by": "YYYY-MM-DD", "source": "<structured Email/Teams source>"}}`. Leave `date` out (a pending decision has no date until it is made; `sweep.py stage` doesn't default one for a pending decision). `made_by` is the person asked (Alan's full name when it falls to him: "can you confirm…" sent to Alan), mapped like an owner by `people map`. `needed_by` only if the message gives a date; resolve "Friday" from the message's Sent date.
- Fill `reasoning` or `options` only if the message states them. Never guess any of the new fields.
- Don't propose a pending decision that is already in the tracker (check `tracker.py read decisions --project CODE`). If a message shows a pending decision was **made** (or withdrawn), stage an **update** to it instead of a second decision, in the same `sweep.json`: `{"op": "update", "table": "decisions", "id": "ABC-D-004", "set": {"status": "Made", "reasoning": "<only if the message states it>"}, "why": "Sara confirmed by email", "source": "<structured Email/Teams source>"}`. `sweep.py stage` dates a made decision the message's Sent day (give `date` in `set` only to override it), keeps the decision's number, and Review shows it as an update for Alan to approve. `set` may hold `status` (Made or Withdrawn), `date`, `made_by`, `needed_by`, `reasoning`, `options` and `revisit`; nothing else (owner, title and project stay with cx-edit and Review). Only a decision that is still Pending is updated; a message that merely discusses it can move `needed_by`.
- A decision that was **made** in a message, as before: `status` `Made` (the default), `date` the Sent date, plus `reasoning`, `options`, `revisit` or `replaces` only where the message states them.

## Promises (BL-125 A)

**Off unless the setting is on (Alan, 13-10-2026).** Look for promises only when `promises.from_sweep` in `system/config/settings.json` is `true`; it ships `false`, and stays off until BL-233's quality data shows enough of the sweep's promises accepted unedited (Alan sets the bar). While it is off, skip this whole section: propose no promise and no promise update. `sweep.py stage` drops any that arrive anyway and counts them as "promises off". Promises from cx-minutes and those Alan adds by hand are not affected.

A separate step from the flow above, in the same `sweep.json`. A promise is a commitment made in passing, lighter than an action: "I'll send the SOW by Friday". Only those **made by Alan or to Alan**:
- **Alan's promises** from Sent Items and his Teams messages ("I'll get you the figures tomorrow"): `promised_by` is Alan's full name, `promised_to` the person he wrote to.
- **Promises to Alan** from incoming mail and chats ("I'll send the extract to you by Thursday"): `promised_by` is the sender, `promised_to` Alan.
- **Promise or action?** A task someone formally asks for or takes on stays an action (step 4); a promise is one person's word to another in passing. Never propose the same thing as both.
- `{"table": "promises", "match": "strong", "values": {"project": "ABC", "promised_by": "<full name>", "promised_to": "<full name>", "description": "<verb first: Send the extract to Alan>", "due_date": "YYYY-MM-DD", "source": "<structured Email/Teams source>"}}`. Resolve "Friday" from the message's Sent date (working-day rule below); with no time given, leave `due_date` out (stage flags `no-due-date`: a promise with no date is never overdue). People are mapped by `people map` like owners. `sweep.py stage` sets `raised` to the Sent day, and a promise already open is logged as a mention (it resets "quiet for N days" in Waiting on), never staged twice.
- **Kept, dropped or moved:** when a message shows an open promise was kept ("here's the extract"), dropped or given a new date, stage an update, not a new promise: `{"op": "update", "table": "promises", "id": "ABC-P-004", "set": {"status": "Done"}, "why": "Sara sent the extract", "source": "<structured Email/Teams source>"}` (`set` may hold `status` Done or Dropped, and `due_date`). `tracker.py read promises --project CODE --status open` lists the open ones. Marking one Done or Dropped is routine in Review (Approve routine covers it, Alan 13-10-2026), unless it carries a `done` block (probably done, BL-218), which is approved on its own.

## Probably done (BL-218)

A separate step, after extraction (step 4) and before stage (skip it when Settings › General › AI drafts › **Spot items that are probably done** is off: the command then lists nothing). Many open items finish without anyone telling creaite: a sent "here's the SOW", a reply saying "approved".
1. Write the messages you read (Sent Items, Inbox replies, Teams) to `system/staging/drafts/messages.json` as `{"messages": [{"source": "<structured Email/Teams source>", "folder": "Sent Items" | "Inbox" | "Teams", "from": "<name> <address>", "to": ["<name> <address>"], "sent": "YYYY-MM-DD HH:MM", "text": "<the lines that matter, at most 600 characters>", "attachments": ["<names only>"]}]}` and run `python3 system/scripts/sweep.py done-candidates system/staging/drafts/messages.json` (read only; it deletes the file itself). Plain code lists, per message, the open items it may close: the item's ID or most of its words, an attachment named like it, the owner as sender or recipient, a completion word, and only items raised before the message, with a hint (Looks done, Maybe done, Not done) and the reasons.
2. **Judge only those candidates.** Does the message say this very item is finished? Add, in `sweep.json`, `{"op": "update", "table": "actions" | "raid" | "promises", "id": "ABC-A-003", "source": "<the message's structured source>", "done": {"strength": "Looks done" | "Maybe done", "quote": "<the words that show it>", "folder": "Sent Items", "reason": "<for Maybe done: why unsure>", "project": "ABC"}}`. Looks done is an explicit completion statement naming the thing, strongest from Sent Items; anything less is Maybe done. A message showing the item is late or moved: `"strength": "Not done"` with `"due_date": "YYYY-MM-DD"` (a re-dating update). Quote the few words only; never copy the message.
3. `sweep.py stage` checks each (open, its own project, raised before; from the owner or Alan, or the words name the owner; Teams counts a little less: Looks done there needs the item's ID) and stages a closing update (status Closed, a promise Done; an action's latest update quotes the evidence) or a re-dating one, with the evidence for Review. It refuses the rest with a note. A closing update is approved on its own, never by Approve routine.
4. **Promises (BL-125 A, Alan 13-10-2026):** open promises are candidates too, by the same rules (the person who made it counts as its owner), but only while the sweep's promises are on (`promises.from_sweep`); while off, `done-candidates` leaves them out and stage skips a promise update.

## Looks like (BL-221)

`sweep.py stage` marks a new item that repeats one in the tracker (same project first, then recently closed, then another project's open item with the same owner), by plain code: the item's ID in its text or subject, the same thread (the subject without Re:, Fw: or [EXT]), a person from the people register in both, a less common word in both, and the item's timeframe (never an item raised after the message). When you can see from the thread that a new item is, or isn't, the same as an existing one, say so on the spec item: `"repeat": {"id": "ABC-A-009", "judged": "same" | "different"}`. "same" makes a Very likely mark **even when plain code found nothing** (BL-297), if the ID is an open (or recently closed) item of the item's project; otherwise it is ignored with a note. Better still, when you are sure, stage the update (4a) instead of a new item. Alan merges, keeps, rejects it, or picks another item to update in Review. Write actions verb-first with their object (BL-220): a vague one (under four words, or no verb) is marked as guessed and offered Sharpen.

## Guessed fields (BL-208)

when a field is your reading rather than something said plainly (an owner named once or by a role, a due date read from "by Friday" or "early December", a decision maker never named, a likelihood read from wording), add `"inferred": [{"field": "owner", "why": "named once, near the end"}]` to the item (fields as stored: `owner`, `made_by`, `due_date`, `needed_by`, `priority`, `impact`, `likelihood`, `type`, `status`, `response_action`). Review's One at a time shows those first, underlined, with your reason. Leave it out when nothing was guessed.

## Sources on items

References only, in the structured format below (`sweep.py stage` skips anything else). Never copy message content into the vault. Every source includes the Sent date (YYYY-MM-DD), and every action and RAID item's `raised` is that date (BL-26).

## Failure handling

- **Microsoft 365 unavailable:** `sweep.py fail --message "…"` (last-sweep.txt is left unchanged so the next run covers the gap), `sweep.py unlock`, and tell Alan; the session-start status line shows it next time.
- **Partial results:** don't stage anything. Record the failure the same way and retry on the next trigger.


## Source references

For every proposed item record the source in the structured format in `references/tracker-conventions.md`: email From (name and address), Subject, Sent date and time (YYYY-MM-DD HH:MM, local) and the Microsoft 365 message link; Teams channel or chat, From, Sent and message link. References only — never copy message content.

**Dates on working days (BL-181).** A due or needed-by date the message states as a weekday stays as written ("by Friday" is Friday). When it gives only a period ("next week", "in a few days") or a date that would land on a weekend without saying so, choose the nearest working day; never invent a weekend date. A weekend date that was written stays, and Review notes it.
