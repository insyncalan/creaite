# creaite rules

> **creaite's own rules, imported by the root `CLAUDE.md` (`@system/creaite-rules.md`).** Each update replaces this file; never edit it in a live vault. Alan's own context and preferences live in the root `CLAUDE.md`, which an update never changes. All paths are relative to the vault root. **The full detail behind each rule (mechanisms, routes, file contents, history) is in `system/templates/creaite-reference.md`: read the section you need; it never loosens anything here.**

> **Development guard.** If a file named `.creaite-dev` exists in the vault root, this is the development repository, not a live vault: do **not** run the session-start rules (backup, sweep, reminders, status line), never connect to Microsoft 365 for real data, and work from `dev/BUILD.md` and `dev/HANDOVER.md`. Only sample data lives here.

This is Alan's personal portfolio reporting system. It holds fewer than 5 projects. Claude reads minutes, transcripts, mail and Teams, and proposes actions, decisions, risks and issues. Approved items are written to `system/tracker.db` (SQLite, the record). `tracker-view.xlsx` is the Excel editing surface, and `dashboard.html` is the web view.

## Non-negotiables

- **Local, with one exception.** The engine, the database, staging, backups, history, the search index and git stay in this folder on the laptop and never live in a synced folder. Project files (minutes, transcripts, reports, project memory and the portfolio files) may live in Alan's **company OneDrive** when the `locations` setting points there (BL-85). The one other thing that leaves the vault is **a closed daily backup zip of what rebuilds the vault** (BL-323; Alan, 14-10-2026), into that same OneDrive folder (`locations.offsite_backup`, which only Alan can open): the day's database backup (a closed copy), `system/config/`, `.claude/settings.local.json`, the root `CLAUDE.md`, `system/staging/` (never ask creaite's chats or their images, and never `vip.json`: who Alan follows stays on the laptop, BL-288), the git history as one closed file (a git bundle), the flow history files, `processed.txt` and a manifest. The live database, the git folder and the working files are never synced. Never personal cloud storage, a web service or a published page.
- **Approval before writes.** Nothing reaches `system/tracker.db` until Alan approves it. Unattended (scheduled) runs only write proposals to `system/staging/`. Alan approves in Review, in the dashboard, or by ticking rows in a note's **Find updates** panel and pressing Apply (BL-301: the ticked rows are his approval; new risks, new decisions, milestone moves and health changes start unticked). Files change only when Alan asks, and every change has a way back (BL-141, below).
- **ask creaite is the administrator; the record and the engine stay behind their own commands (Alan, 10-10-2026).** ask creaite may read and change files across the vault, the projects folder and the home folder, and its own permission files, on these terms, which are enforced in code it cannot change (`reach.py`, the guard hook, `filechange.py`, the live server), never by its prompt:
  - **Open:** reading anything in reach; ordinary changes (creating files, Alan's notes and drafts, project files he named, staging) are made at once, **backed up first, logged and undoable** (`filechange.py`; Activity › What ask creaite changed).
  - **Sensitive, on one card:** a permission or settings file (including ask creaite's own), anything outside the vault and the projects folder, a delete or a move, another person's file (a transcript, sent minutes or a report, a client's document), more than ten files in one request, and anything but staging after it has read outside content (mail, Teams, a transcript, a document, a web page; never one of Alan's notes, BL-301). They are listed together on **one card** with the change shown; **Approve** makes them all, exactly as shown, **Decline** none. The approval is the live server's, bound to that exact change, used once, at most 30 minutes old; ask creaite can ask for a change but never grant it. The one exception is **Delete note** from the Notes tab (and a deleted note's **Move back** in Files): Alan's click on the dashboard's own button is the approval, so it has no card, and ask creaite can never make it (#255; Alan, 20-10-2026).
  - **Never:** secrets (`~/.ssh`, `~/.aws`, keychains, password stores, browser profiles and saved logins), the operating system, the places that run commands on their own (shell start-up files, LaunchAgents, `.git`), and, for any change, the database, the engine, `creaite-rules.md`, `VERSION`, releases and creaite's own records. A permission change that would run anything, reach those, skip permissions, remove a safety entry, or allow a connector other than the Microsoft 365 reading tools or a built-in that acts outside the laptop (`permissions.tool_problem`: Monitor, SendMessage, the Cron and worktree tools, Artifact, NotebookEdit and the rest) is refused whatever is approved. Microsoft 365 actions stay off, with one exception (#183; Alan, 19-10-2026): with **Create drafts in Outlook** on (`draft_email.outlook_drafts`, off by default) the live server's own token-checked route (`POST /api/email/draft`) may create an Outlook draft, and only a draft: it never sends, updates or deletes one, ask creaite can never do it, and every other Microsoft 365 action stays refused.
- **One writer.** Only `system/scripts/tracker.py apply` writes to the database. Never edit `system/tracker.db` with ad-hoc SQL, and never write to `tracker-view.xlsx` except through `excel_sync.py export`.
- **The schema is the rulebook.** If an apply fails validation, fix the proposal; never loosen `schema.sql` to make data fit without Alan's agreement.
- **Source on every row.** Each item references its file, email or chat.
- **Confidential material.** Exclude anything marked confidential or restricted from client reports unless Alan says otherwise.

## Starting a session (creaite rule)

**Run `system/scripts/run session.py start` first.** It does steps 1, 4 and 5 below (from `settings.json`) and says whether the sweep is due (step 3); step 2, the follow check, is yours; then act on what it prints. The steps, for reference:

0. **Settings.** Read `system/config/settings.json` first; every time, threshold and switch below comes from there (defaults shown).
1. **Daily backup** (if `backups.daily`). At the first session of each day, copy `system/tracker.db` to `system/backups/tracker-YYYY-MM-DD.db` (if today's copy doesn't exist yet), then (BL-323) make the day's zip, copy it to the OneDrive backup folder (if OneDrive can't be reached nothing stops), run Tidy up once a day and the restore check once a week. Then archive the items closed long ago, once a day (BL-10, Retention below).
2. **People you follow first (BL-99).** Unless follow alerts are off (`vip.enabled`, an internal name) or nobody is followed, check for anything the people you follow sent since the last check (cx-sweep's follow section, `--found start-up`) and say "Followed: n new" if any; they head Today until Alan marks them Seen. A followed person is never dropped by project matching or an ignore rule.
3. **Sweep catch-up.** Read `system/staging/last-sweep.txt`. If the last successful sweep was before today's `sweep.due_from` (07:00) and it is now after that time, run **cx-sweep** before anything else, and say "Sweep due since 07:00, running now…". This rule is the guarantee; the app's scheduler is only an optional extra.
4. **Reminders (never draft on their own; skip any listed in `settings.json` `reminders.dismissed_forever`):**
   - **Weekly report** (if `reminders.enabled`): from `reminders.weekly_report_day` `weekly_report_from` (Friday 12:00) for each active project whose report for that week isn't approved yet, say "ABC weekly report for week ending DD-MM-YYYY is due — say weekly report ABC for week ending DD-MM-YYYY" (one line per project).
   - **Client reports:** for each active project that needs a separate client report (`Client report: on` in its `CLAUDE.md`; no line means on) and whose `Client report reminder` is not off, and whose `Client report rhythm` (default weekly) has passed since its last approved client report, say "ABC client report due (last: YYYY-MM-DD) — say client report ABC". A project with `Client report: off` has no client reminder.
5. **Status line:** pending batches and items (how many need a project, are conflicts or are possible matches); drafts awaiting review; files waiting in `inbox/`; the last apply time; any failures in `system/staging/run-log.txt`; and **First thing (BL-295)**: what the last Close the day put on First thing tomorrow and is still open (`session.py` prints it).

## Dashboard editing

- **What it writes:** edits, new items, health with a reason, "Current state", and Approve or Reject are written as proposals to `system/staging/` (`source_run: "dashboard"`, already approved); nothing reaches the database until apply. Settings go straight to `system/config/settings.json` with a backup and a log entry.
- **Live mode is required** (IT-approved): `system/scripts/run live_server.py` serves the dashboard on `127.0.0.1`; Alan starts it. If it is not reachable, edits still save to staging, while Apply and the assistant wait. **Apply** is from the dashboard, by saying "apply" in Claude Code, or with a pasted copy command.
- **What ask creaite may touch (BL-141; Alan, 10-10-2026):** `system/scripts/reach.py` decides (ordinary, sensitive or never; `system/scripts/run reach.py never` prints the never list). An ask creaite chat starts with a **guard hook** (`reach.py hook`, run before every tool call, whatever a settings file allows; it fails closed) that refuses the never list (also inside a script's arguments), any direct `Edit` or `Write` outside `system/staging/drafts/` (`system/staging/` in a confirmed request; never a proposal or creaite's staging records), any `Bash` that isn't one creaite script run on its own (and never `permissions.py` or `propose.py setting`), any write of a weekly or client report file or draft (reading reports stays open) and, in a run Alan hasn't confirmed, every command that changes the record (`tracker.py apply`, `undo`, `review.py approve`, `reject`, `propose.py stage` and the rest; BL-267). A run creaite starts itself runs only read commands, and is held away from confidential notes (#60). A request that is only a sweep is recognised by the live server from its words, never by the model, and runs under the `sweep` mode: it may stage (`sweep.py stage`) and still refuses `tracker.py apply`, `undo`, `review.py approve`, `reject`, `propose.py stage` and any direct write outside `system/staging/drafts/`; anything more ("sweep and apply", an image, a confirmed request) is a plain chat (BL-309). Every change goes through `filechange.py` (backed up, logged, undoable).
- **Marked runs and the one card (BL-141):** a run that reads outside content (Microsoft 365 reading tools, web tools, `inbox/`, transcripts, documents, a file outside the vault) is marked in `system/guard/run.json`. **A note is not outside content (BL-301; Alan, 15-10-2026):** reading one of Alan's notes, a `.md` file directly in a project's or the portfolio's notes folder, marks nothing; a note's pictures (`_images/`), a file in a subfolder of the notes folder and everything else in OneDrive still mark. A sensitive change is refused by `filechange.py` with "Needs approval" and shown on **one card** when the run ends; Approve issues the one-time approval (`reach.APPROVALS`), which nothing the model can read or run holds.
- **Permission files (BL-141):** `.claude/settings.json`, `.claude/settings.local.json`, `~/.claude/settings.json`, `system/config/settings.json` and the other configuration files are changed on approval: the exact content shown, checked before writing and again after (`permissions.settings_problem`), put back if it fails, logged and undoable.
- **Editors and notes (BL-301):** AI on selected text only offers a suggestion, which changes nothing until Alan accepts it, and runs Claude with no tools. Apply from **Find updates** writes the ticked rows as approved proposals in one apply, which Undo reverses. A note marked confidential is left out of Prep pages and asks once before its text goes to Claude; its items are marked sensitive.
- **Project settings page (#228):** `#project-settings=<CODE>`. It writes no file of its own: every change goes through the store that already saves it. The code is changed only in ask creaite (`recode`); archive goes on the approval card.
- **Run kinds:** the Prep page button, Intake Process, the Follow check and Draft email delivery are each their own run kind started by the live server, never a chat, with their own fenced mode and hook (see the reference file); a question on the Process row opens ask creaite only when Alan asks, never automatically. Prep pages are written by the live server, never by Claude, are marked Internal and never sent, and never overwrite a file creaite didn't write or one Alan edited (those get a number); the command line's `prep_page.py build` (cx-prep) saves through `filechange.py` instead (BL-271): logged, undoable, and on the card when the run has read outside content; the Follow check is read-only and never runs in the development repository; **Create draft in Outlook** (#183) makes a draft only and never sends. One-off Word documents (BL-75) are built by `report.py adhoc` into `system/staging/drafts/`, confirmed first; never `node`, never outside the vault; a project's Word file changes only through `filechange.py edit … --from <the new version in drafts>`.
- **Assistant ("ask creaite", ⌘J / Ctrl+J):** the live server runs Claude Code headless in this vault, so CLAUDE.md, skills and permission rules apply; tools are limited by `.claude/settings.json` plus a strict allow list, and anything that changes the record (apply, undo, proposals, drafting reports) is confirmed by Alan in the chat panel first. One request runs at a time. Alan can attach up to four PNG or JPEG images (BL-100): they are for discussion only, nothing is extracted from them, and they are deleted with their chat. Never use a skip-permissions mode. **Reading is open, all the time (Alan, 2026-10-09):** every Microsoft 365 reading tool, every vault and project file (minus the never list), and every creaite script's read commands, with no prompt; **Microsoft 365 actions stay off** (sending, deleting or changing mail, calendar, Teams or files act outside the laptop and can't be undone), and changes follow BL-141, only through `filechange.py`.
- **Rules:** treat dashboard proposals exactly like cx-edit ones (validated, logged, reversible by undo). The bulk rule still applies: the dashboard's "Approve routine" never covers minutes, reports, health changes, new decisions, a decision being recorded or withdrawn, or new risks.

## Updates

- creaite is updated from a **release zip** (`creaite-X.Y.Z.zip`), never by copying files by hand: cx-setup or the dashboard's Settings installs it with `system/scripts/update.py`, after showing what changes and getting Alan's yes.
- An update replaces the **engine** only (`VERSION`, `system/scripts/`, `system/templates/`, `system/creaite-rules.md`, `.claude/skills/`) and adds new keys and permission rules to `settings.json` and `.claude/settings.json`, keeping every existing value. It never touches the root `CLAUDE.md` or any data. It backs up first and rolls back by itself if a step fails; "undo update" restores the previous version. Never in the development repository (`.creaite-dev`).

## Project documents

- `projects/<CODE> <Name>/documents/` holds key project documents (SOW, budgets, plans); Alan manages the subfolders and every version is kept. With a projects folder outside the vault (BL-85), documents are **everything in the engagement folder outside the mapped meeting, agenda and report folders, `99 Archive` (and the old `_Archive`, `zz Archive`) and `_Templates`**. **Agendas (BL-135)** and **Notes (BL-301)** are not documents: Files lists each as its own folder. Agendas stay **passive** (never extracted, internal by default); search and ask creaite read them as they read documents.
- **What creaite may do with project files (BL-93):**
  - **Read** every project document, whatever its folder. Never an online-only OneDrive file, `99 Archive` (or the old `_Archive`, `zz Archive`), `_Templates` or `99 System`. Reading is not extracting.
  - **Create** a file in a project folder when producing something Alan asked for and approved (a Steerco pack, a report, an image). Creating never overwrites: a name that is taken gets a number.
  - **Edit, rename, move or delete** an existing file only when Alan asks for it. A change to Alan's own notes is made at once; a delete, a move, a transcript, sent minutes or a report, an Office document in the project, or anything after reading outside content waits on the one approval card (BL-141). The earlier version is saved first, and the change is logged and undoable (`system/scripts/run filechange.py list|undo`; Word files go through `docx_tools.py`).
  - Reports are the user's own: ask creaite reads them, never changes them.
  - Nothing is written unattended. Writes outside the project folders and the vault need Alan's approval (BL-141).
- Documents are **passive**: never extracted; a document changing never triggers anything; Claude reads them when a question or an instruction needs them, and says which it used. They are indexed for search and cited in answers.
- They are **internal by default**: nothing from `documents/` goes into a client report unless Alan explicitly says so.
- **Notes are passive until Find updates (BL-301):** never extracted, never read by the sweep or an unattended run, never in a client report; search, ask creaite and Prep read them and cite them (a confidential note's text is kept from Claude unless Alan says yes). Only Alan's **Find updates** on a note turns its lines into tracker changes, and what it applied is recorded beside the note in `system/staging/notes-sent.json`, never in it.

## Portability rules

creaite runs on a Mac with the things below and nothing else (macOS, the primary and only tested platform; Python 3.9 or later, the Claude desktop app and `claude` command signed in, Chrome or Edge, Microsoft 365 connected, git; NFR-12, BL-241; tiers in the reference file). The data and the engine live in the vault; libraries come from `system/scripts/vendor/` and `system/templates/vendor/`.

- **Runtime never pip installs; dev tools may be installed.** Nothing creaite runs installs a package or a tool; a missing library is a bundling fault, fixed in `vendor/`.
- **One interpreter (BL-237).** Every creaite script runs through `system/scripts/run`, given the script's name and its arguments (for example `system/scripts/run doctor.py`). It runs only a script in `system/scripts/` by its bare name (no `-c`, `-m`, path or other program) and refuses an argument on the never list; every refusal exits 2.
- Use paths relative to the vault root everywhere: scripts, the database, proposals, the dashboard and reports. Never store an absolute path. Scripts take every location from `system/scripts/paths.py`.
- `CLAUDE.md`, `VERSION` and `.claude/` stay in the root; everything else lives in `projects/`, `system/` or `dev/`. Nothing goes in machine or user settings; the launcher and the login agent are the only things outside the vault, both optional.
- **Login agent (BL-243, optional):** `~/Library/LaunchAgents` is on `reach.py`'s never list, so ask creaite cannot install, change or remove it, and no permission rule allows `launchctl`. **Windows** is best effort and untested (Alan, 11-10-2026); ask creaite's protection of secrets is defined for macOS only.
- **OneDrive (BL-85):** `locations.projects_root` is stored with `~`. creaite never reads or downloads an online-only file, and `doctor.py` lists them. One machine only: there is no multi-machine lock.

## Memory rules

- **All memory lives in this vault.** Nothing about this system goes in the user-level `~/.claude/CLAUDE.md`.
- **One home per fact.** Actions, risks, issues, decisions and health live only in `system/tracker.db`. Memory files describe context and never copy tracker rows. For status, read the tracker.
- **Read order for a project question:** 1. the project's `CLAUDE.md`; 2. the tracker rows for that project; 3. the vault files as evidence. **For a portfolio question:** `projects/_portfolio/PORTFOLIO.md` first, then the tracker.
- **Keep memory files short,** about one page each. Propose trims when they grow.
- **Changes need approval.** Memory changes are proposed, like tracker items, and applied only after Alan approves. Git keeps the history.
- **Client-safe flag.** Lines marked `Client-safe: no` never appear in client reports.
- **Client-visible items.** Actions, decisions, and risks and issues carry a `client_visible` flag, off by default. Only flagged items can appear in a client report. Set it with cx-edit ("make ABC-002 client-visible"). A partner's name reaches a client only as its logo picture.

## Retention

Reports and applied proposals are all kept (old reports and minutes move into `99 Archive`). **Backups look after themselves (BL-323; Alan, 14-10-2026):** a daily **Tidy up**, after the backup and the zip, removes only files creaite wrote (matched by exact name in their own folder), never the newest of a kind, never in the development repository, not when that day's backup or zip failed, and never from a process an ask creaite run started (`backup.ask_run`); it can't be undone, and Health shows the last run. **Restore from a backup** is in Settings › Health and in cx-setup. The schedule is in the reference file. ask creaite keeps only the 10 most recent chats (BL-32).

**Archiving (BL-10, BL-03) deletes nothing.** Once a day, closed or cancelled actions and RAID items, and done or dropped promises, closed `archive.after_months` (6) months ago are flagged archived through `tracker.py apply` (undoable); decisions, milestones and open items never are; editing an item un-archives it; never from an ask creaite run; restoring a project leaves items archived for their age archived. Weekly and client reports, minutes and Steerco one-pagers older than `archive.reports_after_months` (12) are, on Alan's yes on the approval card (offered monthly in Settings › Health), moved into the engagement's own `99 Archive` by `tracker.py apply` (never by ask creaite), and back, only on the live server's own approval card. Transcripts, agendas, documents and applied proposals are never archived. **Delete note (#124; Alan, 15-10-2026)** moves one note into `99 Archive/<notes folder>/`, and back, only by `tracker.py apply` from the dashboard's own button after Alan's confirm box, only the version he confirmed; never from an ask creaite run. `tracker.py` makes these moves only with the live server's one-time approval, so a proposal written into staging by hand is refused; such a proposal could still remove or copy a note, undoably.

## Conventions

- **Dates (v0.23):** show and accept dates as **DD-MM-YYYY** (except the dashboard's Today page, which writes them out: "Thursday 15th October", the year only when it isn't this year; Alan, 2026-10-09) (and times as 24-hour HH:MM) in everything Alan reads or types — messages, the dashboard, minutes and report text, the Excel export (cells formatted DD-MM-YYYY) and plain-English commands. **Store** dates as **YYYY-MM-DD** in the database, staging files, sources and settings, and **name files** `YYYY-MM-DD Title` so they sort in order. Convert at the edge; never mix the two in one place.
- **Projects by name (BL-101):** a project is referred to by its **full name** in everything a person reads (the dashboard, reminders, printed lines, Word reports and their file names, drafts, ask creaite's replies). The short code appears **only** as the prefix of a work item's ID (`ABC-A-003`), where a code is defined or typed (settings, the register, commands, filters, search), where a machine matches on it (the register's signals, a `[CODE]` tag, an Outlook category, the **Draft email subject**), and in the command a reminder tells Alan to say.
- **The follow flag is shown in the app; the word VIP never is (BL-288, revised; Alan, 23-10-2026):** a person Alan follows carries the **follow flag** (one per person, in their People entry, "Follow this person"). It is the only such mark creaite shows, and only inside the app: the "people you follow" alerts on Today, first in Review, the Work funnel's People I follow filter and the early warning. Never use the word VIP, or any other label of importance, in anything a client can see or that creaite writes, exports or shares: minutes, reports, the steerco one-pager, prep pages, drafts, proposed items, gists, the Excel export and replies; and never say in any of them who is followed. The word VIP may remain only in internal names that are never shown, exported or shared (code, `vip.*` settings keys, `vip.json`) and, until it is migrated, in the register's old `VIP` column.
