# creaite rules

> **creaite's own rules, imported by the root `CLAUDE.md` (`@system/creaite-rules.md`).** Each update replaces this file; never edit it in a live vault. Alan's own context and preferences live in the root `CLAUDE.md`, which an update never changes. All paths are relative to the vault root.

> **Development guard.** If a file named `.creaite-dev` exists in the vault root, this is the development repository, not a live vault: do **not** run the session-start rules (backup, sweep, reminders, status line), never connect to Microsoft 365 for real data, and work from `dev/BUILD.md` and `dev/HANDOVER.md`. Only sample data lives here.

This is Alan's personal portfolio reporting system. It holds fewer than 5 projects. Claude reads minutes, transcripts, mail and Teams, and proposes actions, decisions, risks and issues. Approved items are written to `system/tracker.db` (SQLite, the record). `tracker-view.xlsx` is the Excel editing surface, and `dashboard.html` is the web view.

## Non-negotiables

- **Local, with one exception.** The engine, the database, staging, backups, history, the search index and git stay in this folder on the laptop and never live in a synced folder. Project files (minutes, transcripts, reports, project memory and the portfolio files) may live in Alan's **company OneDrive** when the `locations` setting points there (BL-85). The one other thing that leaves the vault is **a closed daily backup zip of what rebuilds the vault** (BL-323; Alan, 14-10-2026), into that same OneDrive folder (`locations.offsite_backup`, which only Alan can open): the day's database backup (a closed copy), `system/config/`, `.claude/settings.local.json`, the root `CLAUDE.md`, `system/staging/` (never ask creaite's chats or their images, and never `vip.json`: VIP is private to Alan, BL-288), the git history as one closed file (a git bundle), the flow history files, `processed.txt` and a manifest. The live database, the git folder and the working files are never synced. Never personal cloud storage, a web service or a published page.
- **Approval before writes.** Nothing reaches `system/tracker.db` until Alan approves it. Unattended (scheduled) runs only write proposals to `system/staging/`. Alan approves in Review, in the dashboard, or by ticking rows in a note's **Find updates** panel and pressing Apply (BL-301: the ticked rows are his approval; new risks, new decisions, milestone moves and health changes start unticked). Files change only when Alan asks, and every change has a way back (BL-141, below).
- **ask creaite is the administrator; the record and the engine stay behind their own commands (Alan, 10-10-2026).** ask creaite may read and change files across the vault, the projects folder and the home folder, and its own permission files, on these terms, which are enforced in code it cannot change (`reach.py`, the guard hook, `filechange.py`, the live server), never by its prompt:
  - **Open:** reading anything in reach; ordinary changes (creating files, Alan's notes and drafts, project files he named, staging) are made at once, **backed up first, logged and undoable** (`filechange.py`; Activity › What ask creaite changed).
  - **Sensitive, on one card:** a permission or settings file (including ask creaite's own), anything outside the vault and the projects folder, a delete or a move, another person's file (a transcript, sent minutes or a report, a client's document), more than ten files in one request, and anything but staging after it has read outside content (mail, Teams, a transcript, a document, a web page; never one of Alan's notes, BL-301). They are listed together on **one card** with the change shown; **Approve** makes them all, exactly as shown, **Decline** none. The approval is the live server's, bound to that exact change, used once, at most 30 minutes old; ask creaite can ask for a change but never grant it.
  - **Never:** secrets (`~/.ssh`, `~/.aws`, keychains, password stores, browser profiles and saved logins), the operating system, the places that run commands on their own (shell start-up files, LaunchAgents, `.git`), and, for any change, the database, the engine, `creaite-rules.md`, `VERSION`, releases and creaite's own records. A permission change that would run anything, reach those, skip permissions or remove a safety entry is refused whatever is approved. Microsoft 365 actions stay off.
- **One writer.** Only `system/scripts/tracker.py apply` writes to the database. Never edit `system/tracker.db` with ad-hoc SQL, and never write to `tracker-view.xlsx` except through `excel_sync.py export`.
- **The schema is the rulebook.** If an apply fails validation, fix the proposal; never loosen `schema.sql` to make data fit without Alan's agreement.
- **Source on every row.** Each item references its file, email or chat.
- **Confidential material.** Exclude anything marked confidential or restricted from client reports unless Alan says otherwise.

## Starting a session (creaite rule)

**Run `system/scripts/run session.py start` first.** It does steps 1, 4 and 5 below (from `settings.json`) and says whether the sweep is due (step 3); step 2, the VIP check, is yours; then act on what it prints. The steps, for reference:

0. **Settings.** Read `system/config/settings.json` first; every time, threshold and switch below comes from there (defaults shown).
1. **Daily backup** (if `backups.daily`). At the first session of each day, copy `system/tracker.db` to `system/backups/tracker-YYYY-MM-DD.db` (if today's copy doesn't exist yet), then (BL-323) make the day's zip, copy it to the OneDrive backup folder (if OneDrive can't be reached nothing stops: it is copied the next day it can be), run Tidy up once a day and the restore check once a week.
2. **VIPs first (BL-99).** Unless VIP alerts are off (`vip.enabled`) or nobody is a VIP, check for anything VIPs sent since the last check (cx-sweep's "VIPs" section, `--found start-up`) and say "VIP: n new" if any; they head Today until Alan marks them Seen. A VIP is never dropped by project matching or an ignore rule.
3. **Sweep catch-up.** Read `system/staging/last-sweep.txt`. If the last successful sweep was before today's `sweep.due_from` (07:00) and it is now after that time, run **cx-sweep** before anything else, and say "Sweep due since 07:00, running now…". This rule is the guarantee; the app's scheduler is only an optional extra.
4. **Reminders (never draft on their own; skip any listed in `settings.json` `reminders.dismissed_forever`):**
   - **Weekly report** (if `reminders.enabled`): from `reminders.weekly_report_day` `weekly_report_from` (Friday 12:00) for each active project whose report for that week isn't approved yet, say "ABC weekly report for week ending DD-MM-YYYY is due — say weekly report ABC for week ending DD-MM-YYYY" (one line per project).
   - **Client reports:** for each active project whose `Client report rhythm` (in its `CLAUDE.md`; default weekly) has passed since its last approved client report, say "ABC client report due (last: YYYY-MM-DD) — say client report ABC".
5. **Status line:**
   - pending batches and items, including how many need a project, are conflicts or are possible matches;
   - drafts awaiting review;
   - files waiting in `inbox/`;
   - the last apply time;
   - any failures recorded in `system/staging/run-log.txt`.
   - **First thing (BL-295):** what the last Close the day put on First thing tomorrow and is still open (`session.py` prints it after the reminders; references only are kept, in `system/staging/day-closed.json`).

## Dashboard editing

- **Access:** the dashboard has remembered browser access to the vault (always connected; it asks to "Reconnect vault" only if the browser loses the permission).
- **What it writes:**
  - **Edits and decisions:** edits in the detail panel, new items, project details, health with a reason, "Current state", and Approve or Reject. All are written as proposals to `system/staging/` (`source_run: "dashboard"`, already approved), plus decision fields on existing proposals. Nothing reaches the database until apply.
  - **Settings:** written straight to `system/config/settings.json`, with a backup and a log entry. Client-report rhythms are written to each project's `CLAUDE.md`.
- **Live mode is required** (IT-approved): `system/scripts/run live_server.py` runs on `127.0.0.1` (port in settings) and serves the dashboard. Alan starts it himself (or with the launcher he double-clicks, `launch.py`, BL-86: it starts the server and opens a Chrome app window, and a server it started stops 60 seconds after the last window closes, never mid-job; a server started by hand never stops by itself). If it is not reachable, the dashboard shows a red alert with the restart command; edits still save to staging, while Apply and the assistant wait.
- **Apply:** from the dashboard (through the live server and `tracker.py`), by saying "apply" in Claude Code, or with a pasted copy command.
- **What ask creaite may touch (BL-141; Alan, 10-10-2026):** `system/scripts/reach.py` is the one place that decides: `classify(path, operation)` is ordinary, sensitive or never (the table is in `dev/BUILD.md`, Sprint admin; `system/scripts/run reach.py never` prints the never list). An ask creaite chat is started with a **guard hook** (`--settings`, a `PreToolUse` hook running `reach.py hook`) that Claude Code runs before every tool call, whatever a settings file allows: it refuses the never list (also inside a script's arguments), any direct `Edit` or `Write` outside `system/staging/drafts/` (`system/staging/` in a confirmed request; never a proposal or creaite's staging records), and any `Bash` that isn't one creaite script run on its own (and never `permissions.py` or `propose.py setting`); it fails closed. **BL-267:** in a run Alan hasn't confirmed it also refuses every command that changes the record (`tracker.py apply`, `undo`, `review.py approve`, `reject`, `propose.py stage` and the rest), whatever the permission rules allow; `reach.SCRIPT_COMMANDS` classifies every script command (read, derived, stage, guarded, record), and doctor counts the refusals. **BL-309 (Alan, 13-10-2026):** a request that is only a sweep (cx-sweep's words: "sweep", "sweep mail for ABC", "sweep the last 7 days", "sweep the <subject> thread", "refresh calendar"), recognised by the live server from its words (`panel_sweep` in `live_server.py`), never by the model, is its own confirmation: it runs under BL-295's `sweep` mode, which may stage (`sweep.py stage`, `propose.py people map` on its own draft) and still refuses `tracker.py apply`, `undo`, `review.py approve`, `reject`, `propose.py stage` and any direct write outside `system/staging/drafts/`; anything more ("sweep and apply", an image, a confirmed request) is a plain chat. The run reads the vault, the projects folder and the home folder (`--add-dir`). Every change goes through `filechange.py` (create, edit, move, delete; backed up under `system/backups/files/changes/`, logged in `system/config/files-log.jsonl` and the debug log, undoable with `filechange.py undo`).
- **Marked runs and the one card (BL-141):** the live server marks a run that reads outside content (`OUTSIDE_CONTENT` in `live_server.py`: Microsoft 365 reading tools, web tools, `inbox/`, transcripts, documents, a file outside the vault) in `system/guard/run.json`, which only the server writes; the hook marks it too, before the tool runs. **A note is not outside content (BL-301; Alan, 15-10-2026):** reading one of Alan's notes, a `.md` file directly in a project's or the portfolio's notes folder as `notes.note_of` accepts it (`notes_exempt` in the table, `reach.is_note`), marks nothing (the hook's `reach.read_reason` and the server's own reader agree); a note's pictures (`_images/`, even a `.md` there), a file in a subfolder of the notes folder or one that isn't `.md`, a search over the notes folder, a link named like a note (judged by what it points at), and transcripts, documents and `inbox/` still mark, as before. A sensitive change is refused by `filechange.py` with "Needs approval" and recorded as a request; when the run ends the server classifies each request again, snapshots the content and shows **one card** (`/api/changes/approve`, `/decline`, `/pending`). On Approve it issues a one-time approval per change in its own memory (`reach.APPROVALS`) and calls `filechange.perform` itself; nothing the model can read or run holds an approval. ## Portability rules

creaite runs on a Mac with the things in tier 1 below and nothing else (NFR-12; BL-241). The data and the engine live in the vault; a new machine needs the tier 1 installs, the folder and a Microsoft 365 reconnect.

- **1. Runtime requirements (hard).** macOS, the primary and only tested platform. Python 3.9 or later. The Claude desktop app and the `claude` command, signed in. Chrome or Edge for the dashboard (Safari lacks the folder access it needs). Anthropic's docx skill (document-skills plugin) for Word minutes and reports. Microsoft 365 connected in Claude. git (the command line developer tools) for the vault's history. FileVault on, and the vault in a local folder outside OneDrive and iCloud; with the projects in the company OneDrive (BL-85), its Engagements folder set to "Always keep on this device". Libraries come from `system/scripts/vendor/` (Python, checked against `vendor/manifest.json`, BL-239) and `system/templates/vendor/` (JavaScript).
- **2. macOS conveniences (optional, outside the vault by design).** The double-click launcher and its icon (`launch.py make-launcher`, built with `sips` and `iconutil`), `osascript` and `open` for opening files and windows, and the login agent (below). They hold this vault's location, are not copied with the vault and are made again on a new machine. creaite runs without any of them: start the live server in Terminal.
- **3. Development tools (anyone may install them; never needed to run creaite).** Homebrew (in `~/homebrew`, no admin rights), `gh`, `git` and the Python the tests use, listed in `dev/Brewfile` (BL-240). `gh` also lets "update creaite" fetch a release itself (`update.py fetch`, BL-238); without it Alan downloads the zip by hand.
- **Runtime never pip installs; dev tools may be installed.** Nothing creaite runs installs a package or a tool; a missing library is a bundling fault, fixed in `vendor/`.
- **One interpreter (BL-237).** Every creaite script runs through `system/scripts/run`, given the script's name and its arguments (for example `system/scripts/run doctor.py`), which picks the newest Python 3.9 or later on `PATH` each time and runs that one script, so nothing chooses between `python` and `python3`. The skills, the launcher, the login agent and ask creaite's guard hook use it; the permission rules name it once per script (an older vault's `python` and `python3` rules keep working: an update only adds rules). It runs only a script in `system/scripts/` by its bare name (no `-c`, `-m`, path or other program) and refuses an argument on the never list; every refusal exits 2.
- **"Nothing in machine or user settings"** means the data and the engine: the database, the projects, the memory files, the settings and every script stay in the vault. The launcher and the login agent are the only things outside it, both optional.
- **Windows: best effort, untested (Alan, 11-10-2026).** CI runs on Ubuntu (and macOS, not blocking); nothing tests Windows. `dev/SETUP.md` keeps its Windows commands as unsupported hints (`python system/scripts/<name>.py …`; the wrapper is POSIX `sh`). ask creaite's protection of secrets is defined for macOS only: `reach.py`'s never list names macOS places (`Library/Keychains`, browser profiles under `Library/Application Support`) and would not protect `%APPDATA%`. Making Windows real would start with that list.
- Use paths relative to the vault root everywhere: scripts, the database, proposals, the dashboard and reports. Never store an absolute path. Scripts take every location from `system/scripts/paths.py`.
- `CLAUDE.md`, `VERSION` and `.claude/` stay in the root; everything else lives in `projects/`, `system/` or `dev/`.
- **Login agent (BL-243, optional).** On a Mac, `system/scripts/run launch.py agent install` writes a per-user LaunchAgent (`~/Library/LaunchAgents/app.creaite.<vault folder>.plist`, no admin rights) that starts the live server at login and restarts it only after a crash; a clean stop (Settings › Stop) stays stopped. The server it starts does not stop when a window closes (no `CREAITE_LAUNCHED`). Alan runs it himself in Terminal; `~/Library/LaunchAgents` is on `reach.py`'s never list, so ask creaite cannot install, change or remove it, and no permission rule allows `launchctl`. It lives outside the vault by design, like the launcher (the portability rule's "in the vault" does not apply), holds this vault's location and starts the server through `system/scripts/run` (so a Python upgrade doesn't break it), and is not copied with the vault. It refuses in the development repository and off macOS.
- **OneDrive (BL-85):** `locations.projects_root` is stored with `~` so a new laptop with the same OneDrive works. Set the Engagements folder to "Always keep on this device"; creaite never reads or downloads an online-only file, and `doctor.py` lists them. One machine only: there is no multi-machine lock.

## Memory rules

- **All memory lives in this vault.** Nothing about this system goes in the user-level `~/.claude/CLAUDE.md`.
- **One home per fact.**
  - Actions, risks, issues, decisions and health live only in `system/tracker.db`.
  - Memory files describe context. They never copy tracker rows.
  - For status, read the tracker.
- **Read order for a project question:**
  1. the project's `CLAUDE.md`;
  2. the tracker rows for that project;
  3. the vault files as evidence.
- **Read order for a portfolio question:** `projects/_portfolio/PORTFOLIO.md` first, then the tracker.
- **Keep memory files short,** about one page each. Propose trims when they grow.
- **Changes need approval.** Memory changes are proposed, like tracker items, and applied only after Alan approves. Git keeps the history.
- **Client-safe flag.** Lines marked `Client-safe: no` never appear in client reports.
- **Client-visible items.** Actions, decisions, and risks and issues carry a `client_visible` flag, off by default. Only flagged items can appear in a client report. Set it with cx-edit ("make ABC-002 client-visible").

## Retention

Reports and applied proposals are all kept (archiving them is the rest of BL-03). **Backups look after themselves (BL-323; Alan, 14-10-2026):** a daily **Tidy up**, after the backup and the zip, removes only files creaite wrote (matched by their exact name in their own folder), never the newest of a kind, never in the development repository, not when that day's backup or zip failed, and never from a process an ask creaite run started (`backup.ask_run`: the live server's flag or `system/guard/run.json`; Alan, 14-10-2026); it runs from the session start rule in Alan's own Claude Code session and the live server's daily job; it can't be undone, and Health shows the last run. **Restore from a backup** is in Settings › Health (a dashboard-only, token-checked route that accepts only a zip name from the server's own list) and in cx-setup. The rules (`backups.*`, the same locally and in OneDrive): daily database backups and daily zips every day for 30 days, then one a week (the Monday's) for a year, then one a month (the first) for good; apply, undo, revert and migrate copies 14 days; dashboard snapshots 30 days, then one a month (the `flow-*.json` files for good); release zips: the installed one and the two before it; update backups: the last three; file-change backups 90 days (undo of an older change then says the backup has gone). Other exceptions: ask creaite keeps only the 10 most recent chats in `system/staging/ask/` (BL-32; starting an 11th deletes the oldest), and the debug log keeps only the last seven days (BL-102; the first entry of a new day deletes older files).

## Conventions
